# 발 목표 → 서보 명령 → 피드백 코드 검증

대상: 현재 작업 트리 V41 arcturn. 모터 구동/펌웨어 설치 없이 수행한 코드 및 호스트 검사. 실기 레지스터 readback, 위치 유지, 전체 보행 시험과 구분한다.

## 확인한 전달 경로

1. `arc_turn.h`: CAD/쿠션 발 목표(m), Jacobian(rad 기준), 관절 출력(deg). IK 증분은 rad→deg 변환 후 관절 범위 안에서 계산된다.
2. `robot.c shared_correct`: IMU 0.1° 입력을 rad로 변환해 보정. 최종 관절 목표는 deg.
3. `locomotion_servo.h`: 관절각을 0.1°로 반올림. `robot_config.c`의 leg/joint/ID/center/direction으로 정수 틱 생성. 1회전=4096틱이며 유효 일반 위치는0..4095.
4. `sts3215_sync_positions`: 12개 위치를 먼저 검증한 뒤 2바이트 위치 ×12를 한 Sync Write로 전송. 검증 도중 실패하면 버스 쓰기에 도달하지 않는다. 앞 J2(ID2/5)는 검증된 누적 원점 bias를 더하고 signed-magnitude로 인코딩한다. 무조건 modulo로 명령을 자르지 않는다.
5. 일반 피드백의 앞 J2는 modulo로 정규화하되 검증된 명령 원점을 덮어쓰지 않는다. Stow는 별도 signed 경로/순환 추종 검사다.
6. MuJoCo `cad_physics.py`의 일반 제어는 기본 `embedded_servo_quantization=True`로 같은 C 인코더를 통과한다. Stow는 별도 공용 Stow 인코더를 쓴다. 시뮬레이션에서 정수 틱 변환이 생략된다는 주장은 맞지 않는다.

이 경로에서 ID 누락, 부호 중복 반전, rad/deg 혼동은 발견하지 못했다. 구성 파일과 코드의 일치는 실제 조립 방향/영점의 정확성을 증명하지 않는다.

## 수치 검사

`simulation/mujoco/test_servo_pipeline.py` 추가:
- −120..120°를0.005° 간격48,001개 ×12축으로 인코딩. 양방향 단조성, ID별 중심/부호 일치, 역변환 오차 검사.
- NaN/±Inf/과대 각도는 모든 축에서 거부.
- arcturn 좌/우/전진/후진/혼합6조건 ×128위상에서 인코딩 전후 CAD 발 중심XY/쿠션 최저점Z 비교.
- 기존 펌웨어29개 및 공용 제어16개와 합계48개 통과. 기존 검사에는 signed 전 범위, 회전 경계, 원점 유지, O0/O2 틱 완전 일치 및 전체 정책 범위 검사가 포함된다.

결과:
- 최대 각도 손실0.09375°. 이중 반올림의 이론 상한은 약0.09395°.
- 직접 float→tick 반올림과 비교해 최대1틱 차이. 반올림에 따라 일부 중간 틱이 건너뛰어진다. 소수 계산 전체를 틱 단위로 제한하는 구조는 아니다.
- 시험한 궤적의 최대 발 위치 차이0.535193mm, 최대 높이 차이0.231648mm. 서로 다른 표본에서 발생할 수 있는 최대값이다. 전 작업영역/실제 쿠션 변형에 대한 보증은 아니다.
- 첫 검사 초안은 Python double로 C float의 반올림 중간점을 예상해 실패했다. 기준 계산을 float32 단계로 맞춘 후 통과했으며, 생산 코드나 허용 오차를 바꿔 통과시키지 않았다.

## 발견한 제어/관측 한계

### 관절 피드백이 발 위치 보정으로 연결되지 않음

실물 `robot_shared_drive`는 계획된 발 목표→IK→IMU 보정→서보 목표를 보낸다. `sample_next_joint`의 실측 관절 위치/부하는 안전/추종 진단에 사용하지만, 이 실측으로 네 발 위치를 재구성해 다음 스윙 높이/지지 궤적을 수정하지 않는다. 서보 자체의 위치 제어 루프와 몸체 IMU 보정은 존재한다. “아무 피드백도 없다”는 뜻이 아니다.

따라서 안전 임계값 미만의 추종 오차가 남아도 다음 목표가 진행될 수 있다. 진단상의 stance/swing도 계획된 구간이며 실제 접촉 센서 판정이 아니다. 이 구조로 실제 발 들림을 보장할 수 없다. Python 실험 정책의 추가 encoder 피드백과 실물 C arcturn은 구분해야 한다.

### 순차 피드백의 시간차

정상20ms 프레임마다 한 관절을 읽으므로 각 관절은 기본240ms 간격이다. stall 후보 감시 중에는 해당 축에 집중한다. 12축 동시 실측이 아니므로 읽힌 값을 동일 시점의 다리 자세로 다루면 잘못된 FK가 된다. 소프트웨어에서 단순히 모든 값을 추가 조회하면 버스 시간이 늘어나므로 timestamp/관측기/버스 예산 설계가 필요하다.

### 지연 시 시간축 불일치

`drive_control.h`의 위상/heading 보정 dt는0.02초 고정. `robot.c`는 프레임이 늦으면 deadline을 실제 시각으로 재설정하지만 보행 위상은 여전히20ms씩 진행한다. 명령 속도 진단도 틱 차이×50Hz를 사용한다. 지연 시 실제 궤적 속도와 진단 속도가 달라진다. V40 실기에는618회 지연과 계산 최대24ms/I/O 최대34ms가 있었다. 두 최대가 같은 프레임이었다는 뜻은 아니다. V41 MCU timing은 아직 미확인이다. 단순히 dt를 늘려 다음 각도를 크게 점프시키는 수정은 하지 않았다.

### 일반 위치와 Stow의 경계

일반 보행의 안전/진단 오차는 정규화된 target−actual의 선형 차이다. Stow처럼 회전 경계를 횡단하는 용도로 일반 경로를 재사용해서는 안 된다. 현재 정책 범위 검사를 통과한 일반 궤적에서 경계 문제가 관측됐다는 뜻은 아니다.

## 결론과 변경 범위

이번에는 테스트와 문서만 추가했다. 실제 펌웨어/관절 원점/방향/안전 기준은 변경하거나 설치하지 않았다. 현재 관측된 발 끌림/옆걸음의 확정 원인을 얻은 것은 아니다. 다만 틱 변환 손실보다 실측 관절 추종, 접촉 추정 부재, 시간 지연을 우선 확인해야 할 근거를 얻었다.
