## 오늘 완료한 작업

### 연속 보행과 STM32 업데이트

기존 `trot4 CYCLES PERIOD_MS` 반복 호출은 한 동작의 종료·진단·prompt를 기다리므로
연속 조종에 맞지 않았다. STM32가 gait phase를 유지하는 `drive`를 추가했다.

```text
drive LINEAR YAW SEQ\n    최초 시작
@D SEQ LINEAR YAW\n       목표 갱신 및 heartbeat
@S SEQ\n                  감속 정지
```

- `LINEAR`, `YAW`: -1000..1000. LINEAR 양수 전진, YAW 양수 우회전.
- STM32 50Hz 제어, 앱 heartbeat 200ms, STM32 입력 watchdog 800ms.
- 입력 slew와 motion budget, 2400..1800ms 가변 주기, 혼합 모터별 actuator limit,
  IMU 보정과 tilt/stall safety를 적용한다.
- J1/J3 STS3215와 J2 STS3250의 모터 한계를 유지한다. 기구 대칭 기준은 `stand11`이며
  trot4 FR J1 바깥 방향 2° 보정과 공용 궤적은 이전 작업을 유지한다.
- ESP32는 기존 UART/BLE bridge로 사용한다. 이번 iOS 회귀 수정에 ESP32/STM32
  재플래시는 필요 없다.

실제로 OTA 설치·검증한 STM32 이미지:

```text
revision: continuous-drive-v10
size: 131588 bytes
SHA-256: b66a26041786f8f7195c47bec5177239b655f85b6b327770e6bce3cc56a24984
local artifact: firmware/stm32-learning/Debug/stm32-learning.bin
```

ESP32 staging → STM32 flash → 검증·재부팅까지 성공했고, 이후 `syncstate`에서
revision을 확인했다. 당시 `torque=off safety=ok balance=full`이었다. 이는 당시
조회값이며 현재 상태로 단정하면 안 된다. `Debug/` 산출물은 새 clone에 없을 수 있다.
필요할 때 STM32CubeIDE로 프로젝트를 빌드·재생성한다.

### 로그와 iOS 화면

- STM32 sector 7에서 IMU 보정 1KiB를 제외한 영역에 persistent flight log를 저장한다.
  128-byte 레코드 최대 1,016개이며 동작 경계의 저빈도 사건을 기록한다.
- Mac/iPhone 연결 시 `log time UNIX_EPOCH_MS`로 시간을 동기화한다.
- iOS 상단 고정 검정/녹색 터미널, `연결 → 조이스틱 → 안전 자세 → 단일 보행 → 진단`
  순서, 키보드 완료 버튼, 제공된 앱 아이콘을 반영했다.
- `syncstate`로 자세·토크·안전 상태를 반영하며 저장 로그 조회 버튼이 있다.

### 정지·연결 끊김 수정

다음 코드 경로를 수정했다.

1. 자동 `syncstate`가 보행 중 `stopDrive()`를 호출하던 문제:
   시작 시 예약된 조회를 취소하고 실행 중 상태 조회는 완료 이후로 미룬다.
2. 응답 파서: 줄바꿈 없는 `# `와 이어지는 `$SPOTDRIVE`/`$SPOTSTATE`를 분리한다.
   Swift의 CRLF가 하나의 Character인 점을 반영해 `isNewline`으로 처리한다.
3. 상태 관리: `idle → controlling → stopping → draining → idle`로 관리한다.
   정지 처리 중 `@D`로 세션을 되살리지 않으며, 다음 입력은 종료 확인 후 새 `drive`로
   시작한다. 명령 거부 오류도 세션을 닫는다.
4. 첫 수정에서 추가한 **잘못된 시작 timeout**을 제거했다. 시작 알림이 유실되면
   5초 뒤 앱이 스스로 Ctrl+C와 연결 해제를 실행하던 회귀를 시험으로 재현했다.
   `$SPOTDRIVE started`는 필수 ACK나 연결 유지 조건이 아니다.
5. GATT 쓰기는 한 번에 하나만 ACK를 기다린다. 긴 UART 명령의 chunk는 섞이지 않는다.
   미전송 `@D`는 최신 목표 하나로 교체하고 정지/interrupt 시 대기열을 비운다.
6. 실제 쓰기 ACK가 2초 동안 없거나 전송 오류가 발생하면 연결을 정리한다.
   정지 요청 또는 종료 응답 이후 완료 확인이 5초 동안 없을 때도 정지 요청 후
   연결을 정리한다. 보행 중 시작 알림 유실에는 이 timeout을 적용하지 않는다.
7. 제스처 종료·취소·view 소멸 시 중앙 복귀와 정지를 처리하고 원인을 기록한다.
8. 실제 폰의 송신 enqueue/write/ACK, RX, 상태 전환, scene 안전 정지와 연결 해제를
   시각·uptime과 함께 JSONL로 기록한다. 512KiB 파일 2개로 제한하며 비동기로 쓴다.

- 연결 추적 파일이 simulator app container에 생성되는 것도 확인했다.
- **실제 폰에서 최종 수정 후 지속 보행 성공은 미확인**이다.

  `elapsed=1841ms`, 버스 재시도 0, persistent 결과 `result=ok`였다.

- v10의 `@D/@S`는 ISR에서 처리되어 persistent command log에 기록되지 않는다.
  기록에 `@D`가 없다는 이유로 heartbeat가 안 왔다고 판단한 이전 설명은 잘못됐다.

  앱이 스스로 끊는 timeout, BLE 자체 단절과 반드시 구분한다.
- 이전 CoreSimulator 오류는 샌드박스 밖에서 정상 접근해 빌드·시험했다.
  이를 런타임 미설치나 실제 iPhone 검은 시작 화면의 확정 원인으로 보지 말 것.

## 다른 컴퓨터에서 시작하기

```bash
git clone --branch develop https://github.com/etnlwind/spot_omg.git
cd spot_omg
# 이미 clone했다면 작업 트리를 확인한 후 git pull --ff-only origin develop
conda env create -f environment.yml
conda activate spot_omg
pytest -q
```

iOS 빌드·실기 설치는 Xcode가 있는 Mac에서 한다. 다른 OS의 VSCode/Codex에서도
소스·펌웨어 작업은 가능하지만 iPhone 빌드에는 Mac이 필요하다. 기존 컴퓨터의
`/Users/etnlwind/...`, `/opt/anaconda3/...`, simulator UDID와 DerivedData 경로를
새 컴퓨터에 그대로 사용하지 말 것. `.vscode/`와 STM32
`.settings/language.settings.xml`은 개인 설정이라 이번 커밋에서 제외했다.

```bash
xcrun simctl list devices available
xcrun devicectl list devices
xcodebuild -project apps/ios/SpotOMGController/SpotOMGController.xcodeproj \
  -scheme SpotOMGController -configuration Debug \
  -destination 'platform=iOS Simulator,id=<새 Mac의 simulator UDID>' \
  -derivedDataPath /tmp/SpotOMGControllerDerivedData \
  CODE_SIGNING_ALLOWED=NO -parallel-testing-enabled NO test
```

실기 앱은 Xcode에서 iPhone을 선택하고 개인 Team/서명 자격을 확인한 뒤 Run한다.
bundle ID는 `com.etnlwind.spotomg.controller`이다. 기기를 새 Mac에 연결하고
잠금 해제·신뢰·개발자 모드 설정이 필요한 경우 완료한다.

## 다음 작업: 폰 로그를 먼저 확보

앱 연결 기록은 개발 연결된 폰에서 가져온다. 다른 컴퓨터에서는 새로 조회한
기기 이름/ID를 사용한다. 아래 `UJIN17`은 기존 폰의 이름이다.

```bash
xcrun devicectl device copy from --device UJIN17 \
  --domain-type appDataContainer \
  --domain-identifier com.etnlwind.spotomg.controller \
  --source Library/Caches/RobotConnection/current.jsonl \
  --destination /tmp/spot-ios-connection.jsonl
```

필요하면 같은 경로의 `previous.jsonl`도 별도 이름으로 복사한다. iOS가 cache를
지웠거나 수정 앱을 아직 실행하지 않았다면 파일이 없을 수 있다. 이 경우
로그 부재를 통신 정상/실패의 근거로 삼지 않는다.

읽을 순서:

1. `app-start`의 `joystick-link-v2`로 연결 추적 버전 실행 여부 확인.
2. `tx-write`에 최초 `drive`와 이어지는 `@D`가 있는지, `tx-ack` 간격 확인.
3. 첫 `stop-request`, `scene-safety`, `error`, `disconnected`가 무엇인지 확인.
4. `stop-request`의 제스처/명령 원인과 `phase`를 대조한다.
5. 시작 알림 유실, 종료 prompt 유실, 쓰기 ACK timeout, 실제 BLE 오류를 구분한다.

STM32 로그는 **iPhone의 로봇 BLE 연결을 해제한 뒤** Mac에서 조회한다. 한 bridge에
여러 `spotctl` 프로세스를 동시에 연결하지 말고 아래 명령을 순차 실행한다.

```bash
spotctl --via ble logs --count 80 --output /tmp/spot-stm32-flight.log
spotctl --via ble console send syncstate
spotctl --via ble logs --status
```

폰 앱 trace 다운로드는 iPhone 개발 연결을 사용하고, `spotctl`은 로봇 BLE를
사용하는 별개의 경로다. `BLE device not found`가 나오면 폰의 연결 점유도 확인한다.

그다음 사용자가 로봇을 바로 지지할 수 있는 상태에서 전진 5초 이상 유지 → 손 떼기 →
다시 전진을 시험한다. 필요하면 후진·좌우 회전·대각 입력도 확인한다. 문제 발생 시
양쪽 로그를 먼저 보존하고 원인을 좁힌다. 연결된 로봇에 임의로 보행 명령을 실행하거나
실기 증거 없이 '완료'라고 보고하지 않는다.
