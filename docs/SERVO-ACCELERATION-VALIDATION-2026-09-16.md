# J3 가속도 제한: 확인된 사실과 실제 측정 준비

> 2026-09-16 보행 재개 시 해석 정정: 사용자가 Landing은 J3의 기구적 최대 접힘에서
> 토크를 풀어도 유지되는 자세임을 확인했다. v74/v75 시험은 Stand에서 했으며,
> RR 목표 원시값 증가(1022→1045)는 저장된 방향 -1에서 코드 J3 감소(90→87.98°)다.
> CAD에서는 J3 증가가 접힘이고 Landing 목표도 130°이므로, 아래 당시 기록의
> ‘접힘’ 명칭은 검증된 동작 방향이 아니다. 원시 데이터는 보존하되 접힘 성능이나
> 기구 한계에 막혔다는 결론에 사용하지 않는다. 가속도 동특성은 여전히 미식별이다.
> 사용자가 보행 재개를 요청하여 현재 작업은 오프라인 회수 궤적 검증으로 돌아왔다.

사용자는 시뮬레이터의 RR J3 지연을 지적했고, 실측되지 않은 가속도 제한을
원인으로 단정하지 말라고 지적했다. **현재 우선 작업은 실제 로봇의 응답 측정**이다.
사용자는 이후 **공중 시험 대신 실제 바닥 시험**을 지정했다. 전원 ON·전도 대비·
앱 연결 해제 완료를 확인했고, 현재 자세는 **Landing**이라고 명시했다.
이를 S/Stand 자세라고 가정하지 않는다. 초기 준비 당시에는 실기 모션·설정 쓰기·OTA를
수행하지 않았으며, 이후 연결 복구와 v73/v74 진행 상황은 문서 하단에 기록한다.

## 확정 범위

- 과거 실기 readback: 속도 3400, J1/J3 가속도 50, J2 가속도 254.
  원본 `artifacts/servo-profile-restore-v68/hardware-30s/servo-registers.json`.
- 이것은 레지스터 값의 확인이며 실제 관절 가속도가 439/2232 deg/s²라는
  실측 증거가 아니다. 설치 기체의 보편적인 물리 최대 성능으로도 해석하지 않는다.
- 시뮬레이터 `ServoProfile`은 설정을 100 tick/s² 단위로 환산한 가속도 제한,
  제동 거리 기반 내부 목표, 추정 PD 제어, 추정 20ms 명령 지연을 사용한다.
  이 전체 전달 특성은 실기에서 식별된 모델이 아니다.
- 기존 V69 문서에는 실기는 정상 종료했지만 시뮬레이터가 추종 중단을 예측한
  불일치가 이미 기록되어 있다. 설정 readback 일치를 동특성 검증으로 확대하지 않는다.
- 과거 V70 기록은 축별 약 120ms, 일부 기록은 240ms 간격이다. 이 자료만으로
  20~80ms 구간의 가속도·지연을 확정할 수 없다.

## 실기 측정 순서

1. 준비 확인 완료: 전원 ON, 실제 바닥, 전도 대비, 앱 BLE 연결 해제.
   사용자가 확인한 현재 자세는 Landing. 아래 시험은 접지 하중이 포함된 응답이며,
   무부하 서보 특성 식별과 구분한다. 자세 전환이 필요하면 먼저 사용자에게 설명한다.
2. 읽기 전용으로 revision/pose/torque/safety/12축 상태와 RR J2/J3 설정 확인.
   저장된 모터 원점/방향/누적 J2 좌표를 바꾸지 않는다.
3. 호스트 BLE 조회 왕복 시간을 먼저 측정한다. BLE 수신 시각을 모터 측정 시각으로
   취급하지 않는다. 샘플 간격/명령 시각의 불확실성이 큰 경우 빠른 응답을
   추정으로 메우지 않고 MCU 내부의 단일 축 기록 또는 유선 측정 경로를 준비한다.
4. Landing의 기구 여유와 지지 상태를 확인한 뒤 RR J3의 작은 동일 각도 왕복에서 가속도 설정
   10/30/50을 비교한다. 실제 각 설정 readback, 동일 초기 자세/정지 상태,
   속도 설정, 전압, 반복 횟수, 양방향을 맞춘다. 바닥에서는 작은 2~3°부터
   기울기/다른 발 지지를 확인하고 시험 범위를 정한다. 이전 공중 시험의
   5~10° 계획을 그대로 적용하지 않는다.
   아직 구동 스크립트나 MCU 고속 기록 명령을 실행할 준비가 끝난 것은 아니다.
5. 통신 실패/하드웨어 오류/위치 범위 이탈/과도한 전류·온도·전압 저하 시 중단.
   다른 관절의 자세 유지와 정지 경로를 명확히 한 뒤 실행한다.
6. 설정에 따른 응답 변화가 관측되는지 먼저 판정한다. 정확한 가속도·시작 지연은
   측정 해상도가 충분한 경우에만 식별하고, 별도 반복 기록으로 예측을 검증한다.

읽기 전용 도구(움직임·토크·프로필 쓰기·fault reset 없음):

```powershell
python -X utf8 scripts/hardware/inspect_servo_response_setup.py --output artifacts/servo-acceleration-validation-2026-09-16/preflight-01
```

2026-09-16 현재 검색에서는 Spot BLE 장치가 발견되지 않았고, COM3/4는 Bluetooth
직렬 포트이며 ST-LINK USB 포트는 없었다. 바닥 시험 준비 확인 후에도
`floor-preflight-01` 연결은 장치 미발견으로 종료됐다. 연결 경로를 확인 중이다.

### BLE 연결 진단 후속

- iPhone 앱 완전 종료 확인 후 `floor-preflight-02`도 장치 미발견으로 종료됐다.
- 과거 실기 주소에 대해 Windows WinRT로 광고 검색을 거치지 않는 장치 조회를
  시도했으나 장치 객체를 얻지 못했다. `direct-address-probe-02.json` 참고.
  이것만으로 브리지 전원 고장을 판정할 수 없다.
- 사용자가 ESP32 EN 선이 빠져 있어 다시 연결했다고 알렸다. 직후
  `floor-preflight-03`은 장치 미발견, 이어진 20초 전체 BLE 검색에서도
  Spot 이름/기존 주소/NUS 서비스 후보는 0개였다. 주변 장치 149개는 검색됐다.
  원본: `en-reconnected-discovery.json`.
- 저장소 배선 기준은 **ESP32 EN → STM32 D4/PB5(open-drain)**다.
  `firmware/FIRMWARE_ARCHITECTURE.md` 및 STM32 README에 기재돼 있다.
  `main.c`는 부팅 시에만 LOW 유지 후 해제한다. 실행 중 선을 재연결했다고
  리셋 펄스가 생기는 것은 아니다. 실제 재연결 위치는 아직 사용자 확인 전이다.
- 기존 문서에는 콜드 부팅 실패 시 ESP32 EN 버튼으로 복구된 관측이 있다.
  현재 기체에서도 같은 원인인지, 버튼 리셋으로 복구되는지는 아직 미검증이다.
- 이번 진단에서 서보 동작/토크/설정/펌웨어를 변경한 명령은 보내지 않았다.
  Landing은 사용자 확인 상태이며 연결 후 readback은 아직 없다.

### 연결 복구 및 사용자 요청 자세 전환

사용자가 연결을 다시 확인한 후 `floor-preflight-04`에서 BLE 통신에 성공했다.
실제 설치 버전은 v70이며 초기 자세는 `custom`, 12축 토크 OFF,
서보 설정 addr41/46/47은 모두 0이었다. 제어기의 요청값 3400/254와 다르다.
이는 설정 조회 결과이며 실제 가속도 실측이 아니다.
사용자는 몸통이 바닥에 닿아 있다고 확인했다.

RR J3 정지 상태의 BLE 순차 조회 30회: 수신 간격 중앙값 45.09ms,
산술평균 71.38ms, 최대 179.97ms. 초기 설명에서 45ms를 평균이라고
부른 것은 잘못이며 중앙값이다. 짧은 가속 구간 식별에는 부족하다.

이후 사용자 지시로 Landing→Stand 전환을 완료했다. Stand가 6.37초 걸려
사용자가 이전 빠른 전환 요구를 재확인했다. 목표값 일치로 Stand를 추정하는
옛 로직의 S-native 누락을 확인했고, 명령과 실측 Landing 기준의 v73을 준비했다.
v73에서 실제 Landing→Stand 658ms, `nominal=0`, 최대 오차 18틱으로 확인했다.
[원인·수정·검증 범위](FAST-STAND-V73-2026-09-16.md)를 참조한다.
J3 구동/가속도 비교 시험과 이를 위한 MCU 고속 기록은 아직 수행하지 않았다.

## v74 RR J3 응답 시험 준비

사용자는 빠른 Stand가 정상이라고 확인하고 보행 진단을 계속 요청했다.
네 발 접지, 몸체를 들지 않음, 전도 대비 가능을 다시 확인했다.

- `responseprobe ACC DELTA_TICKS`: RR J3(ID12)만 접힘 방향 12~34틱
  (약 1.05~2.99°) 왕복, ACC는 10/30/50, 속도는 3400. 첫 시험은 23틱(약 2.02°).
- 알려진 Stand 범위, 12축 토크 ON·상태 정상, RR 초기 목표 오차 16틱 이내,
  IMU 기울기 5° 이내를 확인한다. 초기 동작/보호 상태에서는 거절한다.
- 기존 RR 목표를 유지한 채 시험 프로필을 쓰고 41..47 바이트를 실제로 읽어 비교한다.
  200ms 기준 구간 → 500ms 접힘 → 500ms 복귀. 최소 60ms 위치 안정도 확인한다.
- RR은 5ms 주기로 조회를 시도하고, 20ms마다 다른 축을 순회해 상태/이동을 확인한다.
  실제 조회 시작·종료 시각은 MCU `HAL_GetTick()`에 기록한다. 설정 주기 5ms가
  실제 엔코더 표본 주기라고 주장하지 않는다. 실제 간격은 기록 후 계산한다.
- 출력은 측정 종료 후 기존 jointtrace 페이지 전송을 사용한다. BLE 출력 때문에
  구동 중 표본 간격이 길어지지 않도록 측정 루프에서 printf를 하지 않는다.
- 다른 11축 목표, 토크, 앞 J2 누적 좌표를 쓰지 않는다. 정상 종료 시 RR의 원래
  41..47 원시 바이트를 복원/readback한다. 호스트도 12축 40..47을 전후 비교한다.
- 실패 시 자동 재시도/Stand/Relax를 하지 않는다. RR의 신선한 정상 범위 위치를
  읽을 수 있으면 그 위치 유지 목표만 보내며, `hold_sent`는 위치 유지 실측 합격이 아니다.
  통신 불능이면 목표를 추측하지 않는다. 기존 작은 제한 목표가 남을 수 있다.
- 이 시험은 접지 하중의 작은 응답 비교다. 보행 접촉/추진 동기나 모든 관절의 최대
  가속도를 입증하는 시험은 아니다.

호스트 C 8개 통과. 새 시험에는 다른 11축/토크 쓰기 금지, 정상 원시 설정 복원,
다회전 J2 목표 보존, 설정 불일치, 통신 실패, 기울기, 중단, 지지축 이동,
온도, 초기 불안정 및 복원 실패 경로가 포함된다.

v74 빌드: 314,812 bytes, SHA256
`3e6c19c811ab14f77c08fb1e6b7b74f081ac56b48010d9e3377604806c819111`.
OTA 공간 확보를 위해 콘솔/새 진단 소스만 `-Os`, 기존 동작/서보 버스 소스는
`-O0`를 유지했다. 슬롯 크기나 기존 보호를 바꾸지 않았다.

설치 준비는 v73에서 Landing 완료 5,411ms, 최대 오차 19틱 확인 후 Relax,
12개 addr40=0 실측 확인 순서로 수행했다. 증거는 `probe-v74/pre-ota/`에 있다.
v74 설치/재부팅 확인 후 Landing 1,563ms, Stand 657ms로 도착을 확인했다.

### v74 첫 실기 표본과 v75 보완

ACC10, 목표 변화 23틱 시험에서 RR 기준 위치 1007, 원래 목표 1022,
접힘 목표 1045였다. 기존 하중 오차가 있으므로 목표 변화 2.02°와 시작 실측부터의
목표 차이 3.34°를 혼동하지 않는다. 첫 접힘 명령 후 약 50ms에 온도 표본 하나가
41°C→70°C로 변해 즉시 중단했다. 현재 위치 1007 유지 목표를 보냈으며 이후
