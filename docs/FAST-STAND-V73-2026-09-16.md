# Landing → Stand 전환 판정 수정 (v73)

## 사용자 기준

느린 자세 전환은 장애물이 있을 수 있는 불확실한 시작 자세를 위한 것이다.
현재 자세가 Landing으로 인식되고 Stand 명령을 받으면, 선택한 모델의 Stand
목표 각도가 무엇이든 빠르게 일어난다. 특정 모델이나 각도값을 예외 목록에
추가하는 방식으로 해결하지 않는다.

## 실제 관측과 원인

2026-09-16 ESP32 EN 연결 복구 후 설치 버전은 `s-native-v6-2-5-v70`이었다.
초기 12축은 토크 OFF, 사용자는 몸통이 바닥에 닿은 자세라고 확인했다.
사용자 지시로 Landing 후 Stand를 실행했다.

- Landing: `complete-residual`, 10,672ms, 최종 최대 오차 32틱, 토크 ON.
- Stand: `complete`, 6,371ms, `nominal=5520`, 최종 최대 오차 20틱.
- 이전 v57 실기 기록은 빠른 Stand `nominal=0`, 완료 판정 694ms였다.
- `pose_fast_stand()`는 목표 12축이 예전 `robot_stand_targets()`와 정확히
  같아야 빠른 경로를 탔다. 예전 J2는 45°, S-native S의 J2는 약 46.011°다.
  시작 Landing이 확인돼도 목표값 비교에서 탈락했다. 현재 소스에서도 재현됐다.
- 원본: `artifacts/servo-acceleration-validation-2026-09-16/{landing-01,stand-01}/`.

## 수정

- 목표 각도로 명령 종류를 추측하지 않는다. `robot_stand()`가 명시적으로
  `stand_requested=true`를 전달한다. Landing/Stand11은 false다.
- `pose_fast_stand()`는 Stand 요청 여부와 실측 Landing 여부만 본다.
  목표 각도나 보행 모델 이름 비교는 없다.
- Landing 판정은 앱 상태 조회와 같은 축별 80틱 이내를 사용한다.
  이전 빠른 전환의 별도 120틱 문턱을 사용하지 않는다.
- 빠른 경로는 기존처럼 최종 목표를 한 번 전송하고 실제 진전/도착,
  위치 범위, 전압, IMU, 통신 및 중단 처리를 감독한다. `nominal=0`은
  보간 시간을 추가하지 않는다는 의미이며 실제 동작 시간이 0이라는 뜻은 아니다.
- 시뮬레이터도 Stand 명령의 의도를 공용 C 전환 함수에 전달한다.
- 로그의 항상 `slow`라고 쓰던 Stand 시작 문구를 `supervised`로 바꿨다.
- 다른 자세·보행의 목표각, 영점, 관절 방향, 보호 한계를 이 수정으로 바꾸지 않았다.

## 검증 수준

1. 수정 전 C 시험에서 S-native Landing→Stand의 빠른 목표 전송/nominal=0
   조건이 실패함을 재현했다 (`before/`).
2. C 실행 회귀 7개 통과 (`after/`): 기존/Native 빠른 Stand, 일반 자세 감독,
   장애/전압/온도/통신/중단, Stow 누적 좌표, 프로필 레지스터 등.
3. Python 빠른 전환 검사 5개 통과: 예전 목표, S-native 목표, 다른 목표의
   Stand 요청 모두 빠름; 같은 숫자라도 다른 명령은 느림; Landing 밖은 느림;
   명령 전송으로 시뮬레이터 물리 위치를 순간 이동시키지 않음.
4. 관련 시뮬레이터 시험 묶음은 15개 통과, 기존 Stow 물리 시험 3개 실패.
   이전 HEAD의 C 자세 전환 함수를 별도 DLL로 컴파일해 같은 현재 물리 모델에
   대입했을 때 동일한 3개가 실패했다 (`stow-prechange-check/pytest.log`).
   전체 물리 검증 통과로 보고하지 않는다. 새 빠른 전환의 실물 검증과도 다르다.
5. v73 ARM 빌드 327,268bytes (320KiB 슬롯 이내), SHA256
   `10016bdb33013f00ec30d4363b83a3824c858544060a576a9cca6684db30d657`.
   경로: `artifacts/fast-native-stand-2026-09-16/firmware-v73/`.
6. 실기 설치 완료: ESP32 이미지 검증, STM32 플래시 검증/재부팅 완료 후
   `rev=s-native-v6-2-6-v73` readback 확인. 기본 프로필은 V6.2.6이다.
7. 설치 후 실제 Landing 완료: 2,840ms, `nominal=2260`, 최대 오차 26틱,
   토크 ON·safety OK. 응답은 `OK`이며 별도 상태 조회로 도착을 확인했다.
8. 이어서 실제 Landing→Stand 완료: **658ms, `nominal=0`**, 최대 오차
   18틱, 토크 ON·safety OK. 전환 중 건강 이상 표본/통신 재시도는 0이었다.
   이 기체의 이번 자세 전환 1회 검증이며, 보행/J3 응답 시험을 대신하지 않는다.
   원본: `artifacts/fast-native-stand-2026-09-16/post-v73/`.

## 업데이트 준비 순서

이번 설치는 사용자의 몸체 지지 확인 후 Stand에서 바로 Relax를 실행했다.
사용자는 다음부터 먼저 Landing으로 전환하라고 수정 지시했다. 앞으로는
**Landing 전환 → 실제 도착 확인 → 토크 OFF 확인 → 설치** 순서를 지킨다.
설치 후에도 먼저 Landing으로 전환하고 상태를 확인한다. `AGENTS.md`에 기록했다.

CLI의 기본 업데이트 경로에도 Landing 실패/중단/시간 초과를 경고만 하고
자동으로 넘어가는 코드가 있었다. 이제 완료 응답과 `pose=landing`,
`torque=on`, `safety=ok` 조회가 모두 확인되지 않으면 업로드 전에 실패한다.
명시적인 복구용 `--skip-landing`은 별도 기능으로 남아 있으나 일반 업데이트에서
Landing 실패를 우회하려고 자동 선택하지 않는다.
관련 Python 회귀 122개 및 subtest 34개가 통과했다.

## 전환 코드 추가 점검 범위

이번에 확정한 원인은 명령 종류를 목표값 일치로 추정한 빠른 전환 판정이다.
시뮬레이터의 전환 완료 후 자세 라벨 추정, `returning_stand`의 목표 비교,
일반 자세 전환의 시간 기준 완료 판정은 별도로 남아 있다. 보행 준비/정지의
이름 없는 전환까지 포함하므로 이 비교들을 일괄 삭제하면 안 된다.
이 항목들을 모두 실기 이상 동작의 원인으로 확정한 것은 아니다.

실기 Stand 유지 중 `support=servo-health`가 기록됐다. 당시 재조회 12축은
모두 hw=0, 29~46°C이고 위치는 유지됐다. 해당 표시는 지지 보정 정지의
남은 상태이며 `safety=ok`와 별도 필드다. 원인이 된 당시 샘플은 확보하지
못했으므로 단순 표시 오류나 실제 과열이라고 확정하지 않는다.
온도 이상 순간값을 임의로 무시하거나 보호 한계를 올리지 않았다.

J3 응답/가속도 실측은 별도 진행 중이며 아직 수행하지 않았다.
BLE 수신 시각으로 MCU/서보 가속도를 측정했다고 보고하지 않는다.
