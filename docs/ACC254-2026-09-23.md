# 전 축 ACC254 요청 (2026-09-23)

후속 [V96 비동기 피드백 빌드](ASYNC-FEEDBACK-V96-2026-09-23.md)에도 이 변경이
포함된다. 아래 V95 파일과 통신 경로 설명은 ACC 변경 단계의 이력이다.
현재 설치 인계 대상은 V96이며 공유 보행 조회는 IRQ 방식으로 변경됐다.

사용자가 최대값 적용을 요청했다. 기존 보행 기본 요청은 speed3400/ACC254였지만
`robot_servo_profile_acceleration()`이 J1/J3를50으로 낮춰 전송했다.
이 상한을 제거해 모든 축에 요청값을 그대로 보낸다. 코드의 ACC 허용 최대는254이며
255는 기존처럼 거부한다. 낮은 명시 요청과 느린 자세 전환 프로필은 유지한다.
ACC는 가속도 설정이며 최대 속도를50에서254로 올린 것이 아니다.

## 검증 수준

- 호스트 C 검사8종 통과: 안전, Stow 좌표/동작, 자세 감독, 명령 복구,
  프로필 레지스터, 배터리 텔레메트리, 응답 측정 도구.
- 프로필·공유 보행·기존 패킷 최적화 검사37개 통과.
- 추가 actuator 제어 검사2개: O0/Os 모두 통과, 부동소수점 수식 결합 금지.
- heading 크기 최적화 후 navigation V7·공유 보행 검사43개 통과.
  앞 그룹과 중복이 있어 숫자를 합산한 전체 테스트 수로 보고하지 않는다.
- 실제 레지스터 readback, 위치 유지, 하중 보행: 이번 변경으로 수행하지 않음.

회귀 검사는 전 축254 전송, 위치만 갱신한 뒤254 유지, 낮은100 요청 유지,
255 거부, 기존 목표/시간/토크/영점 원시 바이트 보존을 확인한다.
시뮬레이터도 기본254이며 과거 readback50 재현용 명시 상한 검사를 보존했다.
서보가 실제로254를 유지하거나 그 비율대로 가속한다는 증명은 아니다.

## MuJoCo 확인: 보행 문제 미해결

V10 왼쪽 한 걸음, 입력-1000, 들림 보정10mm씩, 간격0,
설정 `[.03,.025,.08,.5,.04,.2]`로 실행했다. 충돌·물리·보호 로직은 유지했다.
전 축254가 유효하다는 모델 가정에서도3.86초에 기울기 보호로 중단됐다.
종료 위치 X+19.3/Y+5.6mm는 보호 이후 이동을 포함하므로 성공한 옆걸음 거리가 아니다.
원시 기록: `artifacts/acc254-2026-09-23/simulation/trajectory.json`.

## 통신 경로 확인

서보 버스는 `servo_bus.c`에서 `HAL_UART_Transmit()`을 호출한다.
송신 중 STM32 수신기를 끄고 송신 완료 후 복구한다. DMA API는 HAL 라이브러리에
있지만 실제 앱 코드에서 호출하지 않는다. 콘솔 송신도 동기 API를 사용한다.
1Mbaud/8N1에서12축 위치 패킷44B의 선로 전송시간은0.44ms다.
DMA는 전송 중 CPU 점유를 줄일 수 있으나 같은 패킷의 선로 속도를 높이지 않는다.
DMA 전환 시 버퍼 수명, 송신 완료 후 RX 복구, 응답/시간 초과 처리를 함께 설계해야 한다.
