# Windows 0.1.3: 정상 정지 후 출력 누락 시 연결 복구

## 0.1.3 추가 확인 — 0.1.2에서 재발

사용자가 중간→최대 입력 중 계속 마우스를 누르고 있었는데 끊겼다고 보고했다.
`spot-omg-console.txt`에는 앱의 `@S 51` → `stopped reason=ok` → ID11 진단
중간에서 출력 종료 → 앱 `^C` 순서가 있다. 앱 오류 배너에서도 종료 로그/프롬프트
시간 초과를 확인했다. **0.1.2는 지연 수신만 처리했고, 끝부분 누락은 해결하지 못했다.**
기존의 느린 재생 시험 통과를 이 실기 문제 전체의 해결로 해석하면 안 된다.

읽기 전용 실제 BLE 조회에서는 `syncstate` 536바이트/5알림/0.14초,
`gaitdiag` 4383바이트/39알림/0.61초가 프롬프트까지 도착했다. 따라서 항상
5초 넘게 걸린다는 근거가 없고, 현재 증거만으로 ESP32·무선·앱 중 어느 층에서
당시 출력이 빠졌는지는 확정할 수 없다. 로봇 동작 명령은 보내지 않았다.

0.1.3은 정상 정지 ACK를 받은 뒤 5초간 진단 수신이 없을 때 한 번만
`\nsyncstate\n`을 보낸다. 미완성 진단 파서를 비우고, 새 상태의 pose/torque/safety와
그 뒤의 프롬프트까지 받은 경우만 연결을 유지한다. 빈 프롬프트만으로 복구하지
않으며, 예약 동작을 취소하고 새 입력 전까지 보행을 재개하지 않는다. 상태 재확인
자체가 5초 안에 끝나지 않거나 정지 확인 자체가 없으면 기존 정지/연결 종료를
유지한다. 진단이 끊임없이 오는 경우의 전체 30초 제한도 유지한다.

Qt UI와 실제 Connection 루프, 가짜 BLE endpoint를 함께 쓰는 시험에서
마우스를 누른 채 중간→최대로 올려 11초 유지했을 때 `@S`는 나오지 않았다.
직접 마우스를 놓은 뒤 사용자 로그의 ID11 누락을 그대로 재생하면 상태 재조회로
복구됐고 Ctrl+C나 두 번째 drive를 보내지 않았다. **사용자가 계속 누르고 있는데
첫 @S가 생긴 원인은 아직 미확정**이다. UI 비활성화·위젯 비활성화·마우스 release,
heartbeat 지연, 입력 변화와 프로토콜 상태 전환을 시각과 함께 기록하도록 추가했다.

검증: Windows 전체 85개 통과. 실제 BLE는 읽기 전용 조회까지 완료했고,
0.1.3의 실제 보행 후 출력 누락/복구 시험은 아직 하지 않았다. 이번에는 펌웨어나
보행 정책을 바꾸지 않았다. iOS 빌드 51은 이전 지연 수신 수정만 포함하며,
이번 출력 누락 복구는 아직 이식·검증하지 않았다.

설치: `%LOCALAPPDATA%/Programs/SpotOMG/V4-0.1.3/SpotOMGController.exe`.
SHA256: `0205e8d52a8b2ccefb08ab925ca6cdfeef27e023e5d870b8b429ef7101a6f350`.
바탕화면/시작 메뉴 바로가기도 0.1.3을 가리킨다. 기존 앱을 사용하는 동안에는
강제 종료하지 않는다. 증거: `artifacts/attitudepd-v4/windows-stop-tail-loss/`.

## 이전 0.1.2 작업 기록 (해결 범위 제한)

2026-09-18 사용자가 V4/V80 보행 중 조이스틱에서 손을 놓으면 연결이 끊긴다고
보고했다. Windows 0.1.1의 종료 로그 수신 시간 제한 문제를 재현하고 0.1.2로 수정했다.
실행 중이던 앱을 정상 종료한 뒤 새 버전을 설치·실행했고 바탕화면/시작 메뉴의
`Spot OMG` 바로가기도 갱신했다. 로봇 펌웨어 업데이트는 필요하지 않다.

## 로그로 확인한 범위

두 보행 모두 `@S` 이후 `$SPOTDRIVE stopped reason=ok`, `OK`, `fall=no`를
출력했다. 첫 종료의 12개 서보 진단 출력 중 앱 송신 `> ^C`가 끼어들었고,
이후 다시 받은 상태는 `pose=stand error=11 torque=on safety=ok fault_code=0`이다.
두 번째도 정상 정지 응답 뒤 진단 출력 중간에서 첨부 기록이 끝났다.

`elapsed=7568ms`와 `5264ms`는 보행 세션의 총 시간이며 Stop 응답 지연 시간이
아니다. 첨부 원문에는 수신 타임스탬프나 앱 오류 배너가 없어 실제 BLE 처리량,
두 번째 종료의 최종 오류 메시지까지 확정하지 않는다. 명시적 BLE 무선 오류가
원인이라는 근거도 이 원문에는 없다.

## 원인과 수정

STM32 `command_drive()`는 보행이 끝나면 종료 응답을 먼저 보내고, 이어서 모든
관절의 상세 진단을 출력한 뒤 콘솔 프롬프트 `# `로 돌아온다. 기존 Windows 앱은
정지 응답을 받아 `draining` 상태로 바뀐 뒤에도 **고정 5초 안에 `# `가 와야 한다**고
판단했다. 정상적으로 진단 패킷이 계속 와도 제한을 갱신하지 않았으므로 시간 초과가
되면 Ctrl+C를 보내고 앱 스스로 BLE 연결을 닫았다.

수정 후 세 단계는 다음과 같다.

- 정지 확인: 기존처럼 최대 5초. 배터리 알림만 받아도 이 제한을 연장하지 않는다.
- 종료 로그 수신: 조각 패킷 수신마다 5초 무수신 제한을 갱신한다. 줄 끝을 기다리느라
  정상 수신을 무응답으로 오인하지 않는다. 전체 수신은 30초로 제한하며, 중복 종료
  알림도 전체 제한을 다시 시작하지 않는다.
- `# ` 수신 후: 상태를 다시 읽고 연결을 유지한다. 출력 도중 새 명령이나 heartbeat를
  보내지 않으며, 이전 스틱 입력을 자동 재생하지 않는다.

정지 미확인 시간 초과와 종료 로그 수신 시간 초과의 앱 오류 문구도 구분했다.
서보 좌표·보행 궤적·펌웨어·토크·보호 기준은 이번 수정에서 변경하지 않았다.

## 재현 및 검증

첨부된 첫 종료 로그 4,278바이트를 fixture로 저장했다. 끝부분은 실제 원문처럼
ID12의 `peak_ctx` 도중에 끊긴 채 보존했다. 테스트는 20바이트/30ms 및
180바이트/300ms로 나눠 전달하고, 이후 합성 줄 끝/프롬프트로 정상 완료를 검사한다.
이 패킷 간격은 시험 조건이며 실측 BLE 간격이 아니다.

수정 전 두 재현 모두 수신 진행 중 약 5초 제한에서 실패했다. 수정 후에는
프롬프트까지 연결 유지·상태 재조회·새 조작 시작이 통과했다. 추가로 부분 줄 수신,
정지 응답 누락, 수신 중단, 프롬프트 없는 무한 출력도 검사했다.

- Windows 프로토콜/연결/배터리/파라미터/UI 및 새 재현: **77개 통과**.
- 기존 MuJoCo V6.1 지지 상태의 Stop→S 복귀 통합: **1개 통과**.
  보행 물리 한계 영향을 분리한 기존 회귀 검사이며 V4 실기 시험을 뜻하지 않는다.
- PyInstaller 빌드와 설치된 EXE의 시작 화면 생성: 성공.
- 새 앱의 실제 창 실행·응답 확인. 실제 BLE 재보행 시험은 이번 수정 후 미실시.

원문, 수정 전/후 시험 결과, 빌드 및 설치 기록:
`artifacts/attitudepd-v4/windows-stop-disconnect/`.

새 창에서 `실제 로봇 · BLE → 연결하기`를 선택한다.
