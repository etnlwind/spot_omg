# 크루즈 속도·매끄러움 개선

가상 로봇 `balance-v4-smooth-sim`. iOS V0.3.3 (9)의 기존 크루즈 선택으로 사용한다.

## 변경

전진 주기 1.05→0.80초, 지지 비율 0.60→0.64, 발 궤적 이동 폭 80→65mm, 들어올림 12→7mm로 조정했다. 한 번에 길게 움직이는 것보다 더 낮은 발 궤적을 짧은 주기로 반복하는 편이 현재 모터·링크 모델에서 이동 속도와 안정성이 좋았다. 몸체 높이, 무게, 접촉 물성, 모터 토크/속도/가속도, 배터리와 BNO055 모델은 그대로다.

빠른 전진 궤적을 그대로 후진에 쓰면 불안정해지는 조건이 있어, 회전/후진에는 검증된 기존 파라미터를 사용한다. 전진 입력 0~500 사이에서 smootherstep으로 두 파라미터를 연속 혼합하고, 위상은 리셋하지 않는다. 보행 궤적과 위상 진행 주기에 동일한 혼합 파라미터를 적용한다. 전진·후진 입력 ±1000은 유지한다.

## 동일 조건 비교

BNO055 능동 보정 ON, nominal 물성, 입력 1000, 14초 구동(안정화 이후 구간 집계).

| 지표 | 기존 | 개선 | 변화 |
|---|---:|---:|---:|
| 평균 전진 속도 | 0.1705m/s | 0.2131m/s | 약 25% 증가 |
| 몸체 roll/pitch 합성 RMS | 1.7806° | 0.8286° | 약 53% 감소 |
| 전진 속도 표준편차 | 0.0887m/s | 0.0623m/s | 약 30% 감소 |
| 최대 roll/pitch | 4.30° | 1.94° | 감소 |

이는 한 nominal 비교 조건의 수치다. 모든 조건에서 같은 비율의 개선을 보장하지 않는다. 결과는 `simulation/mujoco/smooth_cruise_comparison.json`에 있다.

## 검증

25개 전진 후보를 실제 가상 제어기와 변경하지 않은 물리 모델로 비교했다. 전진에 좋은 단일 궤적 후보 두 개는 후진 검증에서 탈락했다. 최종 방향별 혼합 정책으로 nominal 전진/회전→전진/후진/아크/입력 변화, 무거움·낮은 마찰, 무게중심 변화, BNO055 지연 60ms 조건에서 각각 60초 구동 및 8초 정지 관찰을 수행했다. **17조건 모두 안전 정지·발 이외 접촉 없이 정상 정지했다.**

원본 검색: `smooth_gait_search.json`, 최종 17조건: `smooth_cruise_directional_validation.json`. 재현 스크립트는 `tune_smooth_gait.py`, `validate_smooth_cruise.py`이다. `selected.json`의 cruise에 새 기본값과 `turn_reverse_params`를 저장했다.

## 화면 표시

- 화면 갱신이 늦을 때 고정 20ms 물리 스텝을 제한적으로 따라잡도록 수정했다. 기존 루프는 지연 시 경과 시간을 버려 물리 시간이 느려질 수 있었다. 한 번에 최대 4스텝, 0.5초 이상의 긴 중단은 빠르게 재생하지 않는다.
- 실제 재생 배율을 화면과 `imudiag.realtime_factor`에 표시한다. 1.00x가 실제 시간과 같은 속도이다.
- 카메라가 몸체 위치를 즉시 따라 튀지 않도록 0.15초 시정수로 부드럽게 추종한다. 속도 표시는 세계 X축 대신 로봇 전방 속도를 사용한다.
- 카메라·표시 변화는 물리 측정 개선 수치에 포함되지 않는다. 물리 시뮬레이션의 시간 간격은 바꾸지 않았다.

실물 펌웨어에 업로드하지 않았으며, 현장 실측에 따른 보행 이식 검증은 별도다.

최종 Python 전체 257개 및 26개 subtest 통과. 재시작 후 TCP에서 `balance-v4-smooth-sim`, `safety=ok`, `balance=active`, `profile=cruise`를 확인했다. GUI 실행 상태의 재생 배율은 약 1.004x였다. 앱은 V0.3.3 (9)를 유지한다.
