  OTA는 ESP32 이미지 검증 후 STM32 flash 단계에서 완료 응답 시간 초과로 종료됐다.
  이후 읽기 전용 `syncstate`도 console prompt를 받지 못했다(수신 0줄).
  현재 v11/v12 중 무엇이 실행 중인지, 정상 부팅했는지 단정할 수 없다.
- **v12의 24초 전방 동작은 실행하지 않았다.** 사용자 지적 이후 추가
  stand/forward11/relax/재플래시를 실행하지 않았다.
- v11 자세에서 돌아올 때 기본 프로파일 `3400/254`의 `stand`를 실행한 것은
  사용자의 느린 이동 요청을 복귀 과정에 적용하지 못한 실수다.
  OTA의 토크 해제로도 다리가 움직일 수 있다. 사용자가 지적한 빠른 움직임이
  어느 시점에서 발생했는지는 확인되지 않았다.

## 사용자 요구와 실기에서 배운 점

1. 최종 목표는 운반용 최소 부피 자세와, 전원 인가 시 현재 자세를 파악하여
   landing으로 복귀하는 기능이다. 두 기능 모두 아직 완성되지 않았다.
2. 현재 시험 범위는 기본 stand에서 네 다리를 **앞으로 11자 모양으로 천천히**
   뻗는 것까지다. 앞다리를 위로 들어 뒤로 눕히는 후속 단계는 미실행이다.
3. J1/J2 위로 전선이 지나간다. 특히 J2가 기준 상태에서 불필요한 한 바퀴를
   더 돌지 않아야 한다. 같은 자세라는 이유로 목표 각도를 ±360도로 치환하면 안 된다.
4. 사용자는 landing 자세 자체는 괜찮다고 확인했지만, 몸체를 들었을 때의
   움직임을 보고 완전히 눕히는 시험의 출발점을 stand로 바꾸었다.
5. 개별 서보를 차례로 움직인 임시 호스트 스크립트는 정상 stand 동작을 재현하지
   못했다. 기존 펌웨어의 동시 `stand`는 사용자가 잘 섰다고 확인했다.
   다만 정상 도착 확인과 복귀 속도 적합성은 별개다. 이 명령은 느린 복귀 명령이 아니다.
6. 실물에서 J2 `+90°`는 뒤쪽이었다. v12는 전방 후보를 `-90°`로 수정했다.
   수정 방향과 전체 경로의 실물 검증은 아직 없다. 공용 관절 보정값은 변경하지 않았다.

## 저장한 구현과 검증

- `forward_pose.c`의 `forward11`: stand 근처(관절별 120tick 이내)에서 시작,
  J1 실측 위치 유지, J2 `+45° → -90°`, J3 `90° → 0°`를 24초 동안 함께 보간한다.
  매 20ms에 12개 관절을 Sync Write하며, 버스 지연 시 큰 목표 점프로 따라잡지 않는다.
  종료 위치 확인에 최대 2.5초가 추가된다.
- 원시 위치 경계와 반 바퀴 미만 변위를 검사하고 각도 wrap을 하지 않는다.
  이는 현재 인코더 구간의 경로 검사이며, 전원 차단 중 누적 회전 이력이나
  실제 전선 감김을 알아내는 기능은 아니다.
- 수평 기준 roll/pitch 15° 초과, IMU 오류, Ctrl+C는 현재 위치 hold를 시도한다.
  서보 통신/위치/도착 실패 및 safety fault는 torque off를 시도한다.
  hold가 실패해도 torque off를 시도한다. 실제 전도 방지를 보장하지 않는다.
- 새 명령에서는 500ms 넘게 오래된 BNO086 자세 값을 거부한다.
- v12 소스 기준 전체 시험: **176 passed, 25 subtests passed**.
  실제 C 제어 함수를 모의 버스/시계로 시험했으며 ARM 전체 빌드/링크는 경고 없이 통과했다.
  이것은 실기 성공이나 OTA 설치 성공을 뜻하지 않는다.
- 기본 stand 속도, 보행 정책, 전원 인가 시 자동 자세 전환은 변경하지 않았다.

## 다음 작업 순서

### 9월 8일 재개 점검

- Mac에서 읽기 전용 `spotctl --via ble console send syncstate`를 시도했다.
  샌드박스에서는 `BLE is unsupported`, 승인 후 샌드박스 밖에서는
  `Bluetooth device is turned off`로 연결 전에 실패했다. 로봇 응답을 받은
  결과가 아니므로 이전 STM32 무응답의 지속 여부나 현재 설치 버전을 판단할 수 없다.
- Mac Bluetooth 활성화, 로봇 전원, iPhone의 로봇 BLE 연결 해제 여부를
  사용자에게 확인 요청했다. 동작/토크/OTA 명령은 실행하지 않았다.
- 소스 재검토: 기본 `robot_move_to_pose()`는 `robot_hold()`에서 기존 속도
  프로파일을 적용한 뒤 최종 자세를 한 번에 Sync Write한다. 도착 확인은
  기존 2초 제한이므로 단순히 profile만 낮추는 것으로 느린 복귀를 완성할 수 없다.
- `forward_pose.c`에는 20ms 단위 동시 보간과 지연 시 목표 도약 방지 처리가
  있으나, 현재 진입 조건은 stand 근처이며 목적지는 전방 자세뿐이다.
  느린 stand 복귀는 별도 구현 및 경로 검증이 필요하다. 이번 점검에서
  제어 소스나 설치 펌웨어는 변경하지 않았다.

### 통신 확인 후 진행 순서

재조회 결과(사용자가 iPhone 앱 연결을 해제한 후):

- BLE 연결 성공. 일반 CLI는 준비 단계에서 `received 2 line(s)` prompt timeout.
  해당 CLI는 실제 요청 전에 `echo off` 동기화를 수행한다.
- 별도 읽기 전용 진단으로 `syncstate\n`만 보내 원문
  `SPOTBOOT ERROR header\nSPOTBOOT 1\n`을 수신했다.
  STM32가 부트로더 업데이트 대기 루프에 있는 것은 확인됐다. header 오류는
  앱 명령을 부트로더가 업데이트 헤더로 해석했기 때문이다.
  이 응답만으로 flash 손상 여부나 진입 원인을 확정하지 않는다.
- 이전 임시 v12 파일은 현재 Mac에 없다. 대신 기존
  `firmware/stm32-learning/Debug/stm32-learning.bin`이 131588바이트이고
  SHA-256 `b66a26041786f8f7195c47bec5177239b655f85b6b327770e6bce3cc56a24984`로,
  이전에 설치 확인된 v10 이미지와 정확히 일치함을 확인했다.
  벡터는 SP `0x2001fff0`, reset `0x08028595`다.
- 복구 후보는 이 v10 이미지다. 현재 몸통 받침 지지 여부를 사용자에게
  확인 요청한 상태이며, 아직 복구 설치나 동작 명령은 실행하지 않았다.

1. 먼저 읽기 전용으로 통신/부팅/펌웨어 버전/관절 위치를 확인한다.
   무응답이면 전원 및 연결 상태를 확인하고 원인을 좁힌다.
2. 모든 준비·복귀 구간에도 느린 동시 제어를 적용할 방법을 검토한다.
   기본 속도의 `stand`나 과거 개별 관절 순차 스크립트를 자동 실행하지 않는다.
3. 사용자는 이전 OTA 전에 몸통을 받침으로 지지했다고 확인했다.
   재개 시점의 지지 상태까지 자동으로 확인된 것으로 취급하지 않는다.
   OTA 토크 해제는 제어된 느린 이동이 아니다.
4. 통신과 동작 경로를 확인한 뒤 전방 방향과 전선 여유를 단계적으로 실물 검증한다.
   부팅 landing이나 앞다리 후방 접기로 시험 범위를 바로 넓히지 않는다.
