# V90-R1 — 별도 컴퓨터 작업과 병합할 기준

사용자는 V86 작업 컴퓨터에 현재 접근할 수 없으므로 이 컴퓨터의 작업을
**V90-R1**로 명명해 계속하고, 나중에 다른 컴퓨터 코드와 병합하기로 했다.

## 최신 설치 결과 — 10mm 상한 제거 이미지

### Windows0.1.8 조종 잠금 변경

사용자는 벽에 살짝 닿아 보호 정지한 뒤 후진으로 빠져나오려는데 TILT 상태가
조이스틱을 잠그는 문제를 지적했다. 조종 UI 잠금은 자세 명령(landing/stow/
stand/stand11)의 대기·실행·readback 구간과 연결 불가 상태에 한정한다.
일반 상태 조회·정지 완료 대기·보호 정지 중에는 UI를 활성 상태로 유지한다.
`controls_enabled`(UI)와 `can_drive`(현재 전송 가능)를 구분한다. 이전 명령의
완료 응답과 새 명령을 섞지 않으며, 보호 정지 전 누르고 있던 입력은 재생하지
않는다. 스틱을 놓고 새로 조작하면 safety가TILT여도 새 drive를 보낸다.
펌웨어의 새 명령 복구/IMU/기울기/관절 보호와 재거절은 그대로 유지한다.
실기 벽 탈출 동작은 시도하지 않았다. Windows 검사101개 통과.
패키지: `apps/windows/dist/controls-018/SpotOMGController/SpotOMGController.exe`.
이는 Windows 앱 수정이며 펌웨어 재설치는 필요 없다. iOS 잠금 로직은 이번에
수정하지 않았다. 증거: `controls-018-tests.txt`, `app-diagnosis/console-017.txt`.

IMU 재연결 후 I2C0x29 응답 확인. 사용자가 현재 Landing이라고 확인하고
Stand 전환을 요청했다. Landing 오차33틱 확인 후 Stand를663ms에 완료
(오차9틱, safety=ok). 다시 Landing 도착 →12개 토크 OFF → OTA를 수행했다.
이미지 SHA256은 `085fa9d1e91106481aef6d5fd918585358f99f8cf982eab297fa4f8c1422f9c9`.

설치 후 검증도 통과했다(`unbounded-install-imu-restored/verify.json`).
이번에는 준비 후/설치 후 서보0..39 레지스터가 모두 같았다. 전원 차단에 따른
EEPROM 보존 시험과는 구분한다.12개 토크 OFF/정지/오류 없음 확인.
실기에서20/30/256/300mm를 설정·조회했고 범위 표현 초과 입력을 원자적으로
거절했다. 최종 보정값은 모두0mm. 이 값으로 걷거나 다리를 들어보는 시험은
하지 않았으며 큰 값의 설정 성공이 실제 도달 가능성을 의미하지 않는다.
최종 토크 해제 후 custom/error96틱 표시는 안착 후 조회이며 설치 후 Landing
도착 확인과 구분한다. 이전 설치 차단 기록은 아래에 보존한다.

증거: `unbounded-ota.txt`, `unbounded-verify.txt`, `unbounded-readback.json`,
`unbounded-install-imu-restored/`. Windows0.1.7은 이미 실행돼 있으며 이전
0.1.5 창도 남아 있으므로 보정 입력에는0.1.7 창을 사용한다.

## 출처와 버전

### 후속 요청: 10mm 입력 상한 제거

사용자는 실제 들림을 조절하며 확인하기 위한 메뉴이므로 임의의10mm 상한을
제거하도록 요청했다. Windows0.1.7 / iOS 소스 / STM32 / 시뮬레이터에 반영했다.
0 이상의 정수 mm를 그대로 전달하며, 표현 형식은 공통 signed32 양수 범위
(최대2147483647mm)다. 별도의 보행 높이 상한은 없다. uint8 저장을 uint32로
넓히고 native 복사 크기 및 ctypes 형식도 함께 변경해255 초과 래핑을 방지했다.
기존 관절 범위·IK 실패·보호는 유지하며 불가능한 목표를 축소해서 숨기지 않는다.
기존 arc 실험의 ±10mm 계약은 별도 wrapper로 보존한다.

- Windows/UI·호스트·시뮬레이터 검사106개 통과 (`unbounded-tests.txt`).
- 20/30mm Cartesian 실제 Z 증가 및 XY 유지,300mm 입력/readback 저장,
  표현 범위 초과 거절, 도달 불가능한 큰 목표의 원자적 실패를 포함한다.
- 펌웨어: `unbounded-firmware/attitudepd-v4-v90-r1.bin`,325828 bytes,
  SHA256 `085fa9d1e91106481aef6d5fd918585358f99f8cf982eab297fa4f8c1422f9c9`.
- Windows: `apps/windows/dist/foot-lift-017/SpotOMGController/SpotOMGController.exe`,
  빌드 및 무연결 시작 검사 완료. iOS 빌드/설치는 미실시.
- 추가 arc/전용 제어 호환 검사14개 통과 (`unbounded-compat-tests-retry.txt`).
  arc 실험 바인딩의 Mac 전용cc 빌드를 기존 공통 host_build로 바꿔 Windows에서
  검사했다. 최초 컴파일러 미발견 기록도 보존했다.
- 새 이미지 설치 준비 중 BLE 검색 실패 후 사용자가 Windows 앱을 해제했다.
  재접속에서는 Stand/토크 ON/IMU fault11. 정상 Landing 명령은
  `reason=imu-unavailable elapsed=0`으로 모션 전에 취소됐고, I2C 검색에서
  장치가 하나도 발견되지 않았다. 사용자에게 IMU 연결 확인을 요청했다.
  Landing을 생략하거나 IMU 보호를 꺼서 설치하지 않았다. 현재 토크 ON,
  Stand/error9틱이며 마지막 syncstate의 fault는0이나 센서 복구를 뜻하지 않는다.
  아직 로봇에는 아래의10mm 제한 이미지가 설치돼 있다.
  `unbounded-install/prepare.json`, `unbounded-install-retry/prepare.json`,
  `preinstall-landing-recovery.json`, `preinstall-imu.json` 실패 증거를 보존했다.
  IMU 응답 확인 후 새 증거 폴더에서 Landing부터 다시 진행한다.
  사용자의 IMU 연결 확인 후 재조회도 `I2CSCAN: no devices`였다
  (`imu-recheck.txt`). Windows0.1.7 새 창은 실행했다(자동 로봇 연결 없음).

- 기준 커밋: `37544b0` (V81 / attitudepd_v4 / 전용 제어 채널).
- 추가 내용: [다리별 발 들림 설정](FOOT-LIFT-V82-2026-09-21.md).
  V82는 이 기능의 설치 전 임시 명칭이었다. 그 빌드/검사 기록은 보존한다.
- 현재 MCU 식별자: `attitudepd-v4-v90-r1`.
- Windows 패키지: 0.1.6. iOS 빌드 52 소스 준비, Xcode 미검증.
- **V86/V6 코드를 가져와서 이어 만든 버전이 아니다.** V5/V6 보행과
  `originconfirm` 구현의 원본 소스는 현재 저장소에 없다.
- 사용자 지시에 따라 기존 실기 V86 대신 이 작업본을 설치하는 범위가 승인됐다.

## 나중에 병합할 때

다른 컴퓨터의 V86 소스를 먼저 독립 브랜치/커밋으로 보존하고 공통 조상에서 비교한다.
버전 숫자만 보고 V90-R1이 V86의 모든 기능을 포함한다고 판단하지 않는다.

1. V86의 관절 원점 확인, 전원 재인가, Landing/Stand 변경을 우선 검토한다.
   이 기능을 누락시키거나 단순 충돌 해결로 제거하지 않는다.
2. V5/V6 프로필의 인덱스·궤적·보호와 V90-R1의 공통 발 들림 설정을 결합한다.
   V90-R1의 V4 분석은 V6 실기 앞발 들림의 원인 분석이 아니다.
3. STM32 `foot_lift.h`, native goal 보정, console 설정/readback 및
   Windows/iOS 설정 UI, 시뮬레이터 경로를 함께 반영한다.
4. 0mm 원본 보존, 개별 발 보정, 접지 중 높이 유지, 시작/정지와 새 V5/V6
   궤적의 위상/관절 한계를 다시 검증한다.

## 빌드와 설치 진행

`artifacts/foot-lift-v90-r1/firmware/manifest.json`에 리뷰된 이미지 해시가 있다.
명칭/앱 호환 수정 후 Windows 관련 검사 45개 통과 (`rename-tests.txt`).
이전 100개 호스트 및 9개 새 시뮬레이터 검사 증거는 `artifacts/foot-lift-v82/`에 보존한다.

V86 설치 전 실제 조회: custom, 오차141틱, 토크 OFF, safety OK, 12개 서보 정지.
Landing 명령이 다음 오류로 거부되었으며 모션/OTA는 실행되지 않았다:

```
ERROR: origin unconfirmed; requires ALL-servo power cycle in Landing and explicit originconfirm; no motion sent
```

기록: `artifacts/foot-lift-v90-r1/hardware-install/prepare.json`, `prepare.txt`.
사용자가 물리적 Landing 자세에서 모든 서보 전원 재인가 및 앱 연결 해제를 확인했다.
V86의 저장 로그에서 실제 명령 `originconfirm servo-power-cycled-in-landing`을
확인해 실행했고 `ready=1 motion_sent=0` 응답을 받았다. 이 명령은 사용자에게
전원 재인가를 확인받은 경우에만 사용한다. MCU 재부팅으로 대체하지 않는다.

## 설치 완료 및 검증 범위

- 이미지: 325664 bytes, SHA256 `50c5b8877a23563cafc1b5f855f94b996849f5d8fa4e0acc79ffc4b22a18161a`.
- 준비: Landing 실제 오차25틱, 12개 토크 OFF 확인.
- OTA: 이미지 검증 및 재부팅 완료, 실기 `rev=attitudepd-v4-v90-r1` 확인.
- 설치 후 Landing: `complete-residual`, 오차25틱. 이후 Relax 수행.
- 설정 readback: FL/FR/RL/RR=10/3/0/7mm 설정·조회 성공, 최종 모두0mm 복구.
- 12개 서보 토크 OFF, 정지, hw=0 및 safety=ok/fault_code=0 확인.
- 토크 해제 후 안착하면서 최종 표시는 custom/error91틱. 토크 ON 상태의
  Landing 도착 검증과 구분하며, 표시를 바꾸려고 반복 모션을 보내지 않았다.
- Windows0.1.6 패키지 빌드/무연결 시작 검사 통과. iOS 소스만 준비됐다.
- 실기 독립 위치 유지 시험, Stand/보행/추가 들림 효과 검증은 하지 않았다.

### 설치 검사에서 발견한 레지스터 차이

일반 설치 검사 `verify.json`은 전체0..39 주소가 같아야 한다는 조건에서 실패했다.
실제 차이는 앞 J2 ID2/5의 최대 위치(주소11/12)가4095→0인 것뿐이다.
기존 `stow_motion.c`의 `robot_reference_pose()` → `limits(true)`가 원점 확인 전에
이 값을 쓰며 lock55=1로 처리한다. 이번 발 들림 구현이 추가한 쓰기가 아니다.
전원 차단 후 영구 보존 여부는 시험하지 않았으므로 “EEPROM 불변” 검증 통과로
보고하지 않는다. 다른0..39 설정은 동일했다. 자동 검사의 실패 기록은 보존했고,
Landing 확인 후 Relax 및 별도 readback으로 마무리했다. V86 병합 시 원점/모드
처리 차이를 반드시 비교한다. 한계값을 수동 복원하거나 검사를 무조건 완화하지 않았다.

증거: `artifacts/foot-lift-v90-r1/ota.txt`, `origin-confirm-explicit.json`,
`hardware-install/retry-01/{prepare,ota-result,verify,post-verify-relax}.json`,
`config-readback.json`, `startup.png`. 이전 실패 기록은 덮어쓰지 않았다.
# Windows 0.1.9 재입력 수정 및 제어 경로 점검 (2026-09-21)

- `Controller.sample_input`에서 release/new-press를 추적한다. 종전 연결 루프는
  새 press가 idle일 때만 재입력을 허용하여 stopping/draining/read 대기 중 잡은
  스틱을 잃었다. 정상 stop 응답이 뒤늦게 도착하며 새 press를 다시 무효화하는
  문제도 수정했다. 이전 명령 완료 전 중복 drive를 보내지는 않는다.
- 대기 중 놓은 제스처는 재생하지 않으며 보호 정지 당시 잡고 있던 스틱은
  자동 재시작하지 않는다. 새로운 조작은 정지 대기 중에도 인정한다.
- Windows 앱 전체 106 tests 통과. 최종 latch 초기화 보완 뒤 관련 62 tests 재통과.
- `test_control_channel.py`에 로그 폭주 중 @D가 0.7초 동안 3회 이상 유지되는
  연결 루프 시험 추가. 앱 제어 8 tests + 실제 C/C++ 경로 호스트 2 tests 통과.
- 코드 점검: 앱 제어 RX/TX는 BLE 005/006, 콘솔은 002/003. 콘솔 데이터는
  제어 상태 파서에 넣지 않고, 제어 응답은 요청 sequence와 DATA/DONE으로 처리한다.
  ESP32는 로그 16KB 대기열과 제어 프레임을 분리하고, STM32는 로그 대기열보다
  제어 응답/다음 명령을 우선 처리한다. @D/@S는 UART 수신 ISR에서 처리한다.
- 한계: ESP32↔STM32의 115200 UART와 BLE 무선은 공유한다. STM32 제어 응답의
  `write_wire`는 HAL_MAX_DELAY 동기 전송이다. ESP32 `routeUartByte`는 같은 loop에서
  `indicate()`를 호출한다. 설치된 Arduino ESP32 3.3.11 라이브러리는 indication
  확인을 기다리므로 UART 수신 처리가 그동안 지연될 가능성이 있다. 설치 브리지의
  정확한 라이브러리 버전과 실기 최악 지연은 이번 시험으로 입증하지 않았다.
  호스트 시험의 UART/BLE는 mock이므로 실제 지연/무선 손실 검증과 구분해야 한다.
- 이 변경은 Windows 앱만 갱신한다. 로봇/ESP32 펌웨어와 iOS는 이번에 변경·설치하지 않았다.
- 실행 파일: `apps/windows/dist/controls-019/SpotOMGController/SpotOMGController.exe`.
