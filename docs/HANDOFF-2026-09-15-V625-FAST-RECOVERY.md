# V6.2.5 / V70: 빠른 회수·추종 회복 실기

V69 handoff 이후의 최신 상태다. 사용자가 빠르다고 본 동작은 **S 복귀**다.
이를 토크 해제 뒤 중력 낙하로 설명하지 않는다. 사용자는 보행 주기 숫자보다
실제 다리 이동 속도와 뒤로 뻗는 정도를 원한다. 사진의 약 90°는 아래 링크와
바닥 사이의 투영각이며 J3 서보 각도 90°라는 뜻이 아니다.

  기본값, simulator 기본값을 갱신했다. 앱은 소스/빌드 검증이며 폰 설치는 안 했다.
- 바이너리 `artifacts/s-native-v6-2-5/firmware-initial/s-native-v6-2-5-v70.bin`,

- OTA 완료 및 실기 revision 확인. 클럭 변경 없음: 실제 84MHz.
- 마지막 30초 입력 시험 정상 정지 후 torque=off, safety=ok, fault_code=0.
  후속 readback에서도 확인. health 12개 hw=0, 10.8~10.9V, 30~34°C.

## 수정과 근거

V69 기록을 C 추종 제어기에 재생하면 초기 구간의 평균 위상 진행률은 0.3555다.
기존 오차 감속 뒤 회복은 0→1에 5초가 걸렸고, 관절별 피드백은 약 240ms마다
새로 들어왔다. V625는 회복 시간을 0.5초로 줄이고 프레임마다 두 관절을 읽는다.
실기 표본 간격은 약 120ms로 확인했다. 오차 6~14° 감속 곡선, 14° 정지,
stale/지속 실패 중단은 유지한다. 정지 복귀는 기존 동작을 유지한다.

회수 초반 20%는 들어 올림에 사용하고 수평 이동을 20~80%에 집중한다.
기본 주기 1.0초와 앞뒤 도달 목표는 유지한다. C/Python 궤적을 함께 변경했다.
S 출발, FR·RL 동시 첫걸음, FR만 첫 J1 변화량 2배, 이어지는 정상 오므림,
대각선 X/Z 공유, “하나, 둘” Stop→S 규칙을 유지한다.

기록은 256명령+512표본으로 늘렸다. `jointtrace stop`은 다음 Stop에서 기록을
시작하게 하며 자체로 움직이지 않는다. 페이지 총 768행을 검증한다.

## 실기 비교와 재실행

- 15초 입력 시험: 정상 정지 elapsed=13082ms, 1304 samples,
  최저10.7V, lag=46/lag+droop=46, late=1, derate=recommended, fall=no.
- V69와 공통 240ms 격자로 비교한 1.0~4.8초 초기 구간에서 네 관절 평균
  이동량/초는 J2 17.85→25.59°/s(1.43배), J3 14.36→20.73°/s(1.44배).
  표본 기반 이동량이며 순간 최고 속도나 몸체 이동 속도가 아니다. 전압도
  완전히 일치한 A/B 시험은 아니다. 재생 위상 진행률은 0.5147로 증가했다.
- 12축 실제 설정 readback은 speed3400, J1/J3 acceleration50, J2=254다.
  `profile`은 요청값일 뿐이므로 실제 레지스터 readback과 혼동하지 않는다.
- 사용자 “다시한번 보자” 요청으로 같은 모델/100% 입력 30초 재실행.
  정상 정지 elapsed=28448ms, 2828 samples, 최저10.3V,
  lag=121/lag+droop=121, late=8, limited=0, derate=recommended, fall=no.
  Stop 직후 readback pose=stand error=8(약0.70°), torque=off.
  독립적인 토크 유지 시험은 아니다. 이후 무토크로 처진 custom 오차를
  Stop 실패로 해석하지 않는다.
- 30초는 내부 S 진입을 포함한 호스트 입력 시간이다. 정확한 30회 또는
  순수 보행 30초를 측정했다고 쓰지 않는다. 몸체 고정/발 공중 조건이다.
- 재실행의 공통240ms 격자 비교는 J2 17.85→25.58°/s(1.43배),
  J3 14.36→22.37°/s(1.56배)였다. 재생 평균 위상 진행률0.5081.
- 첫30초 trace 전송은 BLE시간 초과로 끊겼다. 원본 실패는 보존했고,
  재연결로 같은 RAM기록256명령+512표본 전체를 검증해 복구했다.
  `hardware-30s/summary.json`의 error는 첫 전송 실패다.
  최종 자료는 `jointtrace-retry.txt`, `trace-recovery.txt`,
  `post-run-readback.txt`, `joint-analysis/`이다. 추가 동작 없이 읽기만 했다.

## STM32 클럭 질문

HCLK84MHz, APB1 42MHz, APB2 84MHz, SysTick83999, PLLready, Flashwait2를
직접 readback했다. V69는 1357프레임 중 late3, 계산 구간 최대11ms,
I/O최대34ms. V70 마지막 시험은 약1414프레임 중 late8,
계산 구간 최대14ms/I/O최대36ms다. 구간 경과 시간은 순수 CPU시간과 다르다.
현재 자료에서 클럭이 평균적인 큰 감속의 주원인이라는 증거는 없고, 추종
진행률 제한이 기록에서 확인된다. CPU를 올려도 20ms 정책 주기나 UART 대기
자체는 사라지지 않는다. 클럭은 그대로 두고 로직 변경 효과를 비교했다.
최대180MHz 지원 근거는 [상세 보고서](S-NATIVE-V625-2026-09-15.md)의 ST자료.

## 검증 수준과 남은 일

- 호스트 83개/C7개/trace17개 통과, iOS simulator 빌드 성공.
- 추가 기존 검사49개 통과, V621 바닥 동역학2개 실패: 설치된 가속도
  `[50,254,50] × 4`를 반영하면 tilt중단, 예전cap254면 통과하는 A/B 확인.
  통과시키려고 실제 제약을 제거하지 않았다.
- V625 몸체 고정 시뮬레이션은 정상 Stop→S(최종0.219°), 내부 접촉0.
  보행 순간 최대오차24.0°, Stop32.7°. 순차 표본의 보호 기준이 모든 순간
  관절오차를14° 이하로 보장하는 것은 아니다.
- V625 바닥 시뮬레이션은 시작0.96초 뒤 tilt중단. **바닥 보행 성공 미검증**.
- 실제 속도 향상은 확인됐으나 뒤로 뻗을 때의 바닥 대비 각도, 접지 동기는
  검증되지 않았다. 사용자 시각 피드백 질문이 대기 중이다. 15초 초기기록
  J3 최대 표본오차16.6~20.2°로 추종 개선 여지가 남는다.
- 마지막 시험에 전압10.3V와 감속 권고가 있어 이후 속도 비교 시 전원 조건을
  고려한다. 같은 조건의 반복 실행을 무제한 이어가지 않는다.

## 후속 앱 변경: 충전 경고

사용자가 정지 전압10.8~10.9V와 동작 최소10.3V를 확인한 뒤 충전을 위해
실기 테스트를 중단했다. Windows/Mac/iPhone 모두 충전 경고를 요청했다.
11.0V 충전/10.5V 즉시 중단 경고와 새 전압 스트림용 V71을 구현했다.
**실제 보드는 아직 V70이며 추가 구동/OTA 없음.** Mac 앱 배치 완료,
아이폰은 잠금으로 설치 대기, Windows는 업데이트 소스 패키지 제공.
[구현·검증·배포 상태](APP-BATTERY-WARNING-2026-09-15.md).
