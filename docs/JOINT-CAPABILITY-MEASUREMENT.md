# 실제 관절 동작 능력 측정 — 구현 및 시험 제안

2026-09-12. 대상: J1/J3 STS3215, J2 STS3250. 위치 제어 기준은 [STS3250-POSITION-CONTROL.md](STS3250-POSITION-CONTROL.md)를 따른다.

## 이번에 만든 것

**V47 진단 펌웨어 + `spotctl analyze-joints` 분석기.** 보행 목표를 변경하지 않고, 실제 전진과 턴에서 명령한 움직임과 관측한 움직임을 비교한다. 빌드·호스트 검증과 V47 실물 설치·전진/좌/우 각1회 단기 측정을 완료했다. 정밀 지연 식별·물성 보정은 아직 미완료다. 모터 교체가 필요한지는 아직 결정하지 않는다.

1. STM32 `jointtrace arm`: 다음 보행의 기록을 준비한다. 토크/자세/보행 명령은 보내지 않는다.
2. 실제로 전송에 성공한 12축 목표를 전송 시작·종료 시각과 저장한다.
3. 기존 안전 감시용 서보 조회 결과를 요청 시작·종료 시각과 저장한다. 그 조회 때 유효한 명령 번호에 연결한다. 서보 조회 추가, 통신 출력, Flash 쓰기를 보행 루프에 넣지 않았다.
4. 위치, 속도 원시값, 부하 원시값, 전류 원시값, 전압, 온도, 하드웨어 오류, 읽기 실패를 보존한다. 읽기 실패를 위치0으로 분석하지 않는다.
5. 정지 후 `jointtrace dump`로 내려받는다. 분석기는 CSV·JSON·한국어 Markdown 보고서를 생성한다.

기록 용량은 명령256개/조회256개이며 정상50Hz에서는 약5.12초다. 가득 차면 기존 기록을 보존하고 추가 기록만 중단한다. **로봇을 자동 정지시키는 기능은 아니다.** RAM 약14KiB를 사용하고 전원 차단·리셋 시 사라진다. 정지 후 먼저 내려받는다. 기존 안전 감시·정지 조건은 그대로다.

## 첫 시험: 잘 되는 전진과 끌리는 턴 비교

같은 보행 정책, 배터리 상태, 쿠션, 바닥을 사용한다. 시험별로 Stand에서 시작해 전진/좌회전/우회전을 각각 일정한 조작 크기로 실행한다. 정책 전환은 기록 준비 전에 끝낸다. 시작 혼합 구간과 정상 보행을 구분하기 위해 분석 구간을 지정한다.

절차:

1. V47을 설치하고 `syncstate`에서 `rev=shared-locomotion-v47`, `caps`에 `jointtrace`를 확인한다. 설치 방법은 readme의 기존 펌웨어 절차를 따른다. 실기에서 V47과84MHz를 확인했다.
2. 앱에서 원하는 정책과 Stand를 준비하고 정지 상태에서 아래 기록 준비 명령을 실행한다. CLI의 기존 앱 BLE 인계 기능을 사용할 수 있다.
3. 앱으로 재연결하여 한 방향만 약5초 조종하고 Stop한다. 기록기가 가득 차도 보행은 계속되므로 Stop은 별도로 해야 한다.
4. 정지 후 아래 명령으로 새 파일에 내려받는다. `arm`을 다시 호출하면 이전 기록이 지워진다.
5. 같은 순서로 전진·좌회전·우회전을 각각 저장한다. 초기 측정 후 재현성을 확인하기 위해 조건별3회 반복을 권한다.

```sh
# 기록 준비: 움직임을 시작하지 않음
spotctl --via ble console send 'jointtrace arm'

# 위 명령 후 앱에서 전진 시험 → Stop. 정지 후 다운로드.
# 같은 파일에 여러 dump를 append하지 않도록 시험마다 새 이름 사용.
python tools/download_joint_trace.py --output artifacts/forward-01.log

# 다시 arm → 앱에서 좌회전 시험 → Stop 후 저장
python tools/download_joint_trace.py --output artifacts/left-01.log

# 다시 arm → 앱에서 우회전 시험 → Stop 후 저장
python tools/download_joint_trace.py --output artifacts/right-01.log

# 첫1초를 제외한 같은 구간끼리 비교. 실제 시작 기록을 보고 구간 조정 가능.
spotctl analyze-joints artifacts/left-01.log --compare artifacts/forward-01.log \
  --start-ms 1000 --end-ms 5000 --output artifacts/joint-left-vs-forward
spotctl analyze-joints artifacts/right-01.log --compare artifacts/forward-01.log \
  --start-ms 1000 --end-ms 5000 --output artifacts/joint-right-vs-forward
```

`jointtrace status`는 기록 수·가득 참 상태를 조회한다. `jointtrace off`는 정지 상태에서 기록만 종료한다. `arm/off/dump`는 보행 중 거부한다. `jointtrace dump OFFSET COUNT`는 최대12개 레코드만 반환한다. 다운로드 도구가 묶음 번호·개수·전체 개수를 확인하며 전체를 조합한다. 각 묶음의 타임아웃은20초이고 누락되면 완성 파일로 저장하지 않는다. 기록 준비 후 별도 모션 명령을 보내지 않으면 데이터는 생기지 않는다.

## 보고서와 판정

- `commands.csv`: 전송 시각과 모든 관절의 목표각. 실제 전송된 목표에 대한 기록이다.
- `samples.csv`: 각 조회 시각의 목표각·실제각·오차 및 원시 피드백. 12축이 동시에 측정된 것처럼 묶지 않는다.
- `joint-capability.json`: 관절별 목표/관측 진폭, RMS·최대 오차, 샘플 사이 평균 속도, 샘플 간격, 최저 전압, 오류와 지연 식별 상태.
- `report.md`: 한국어 요약 및 전진 대비 턴의 관절별 RMS 오차 차이.

| 관측 | 다음 수정/시험 |
|---|---|
| 턴의 목표각 이동량부터 작음 | 해당 각도를 CAD 발끝 궤적으로 환산해 실제 목표 여유가 부족한지 확인. 전진과 턴은 방향이 달라 진폭 숫자만 같게 복사하지 않는다. |
| 목표는 충분한데 실제 이동량이 작거나 오차가 큼 | 서보 속도·가속도 설정 readback 및 지지/스윙 구간별 부하·전압과 비교 |
| 관절은 목표를 따라가지만 발이 끌림 | 기구 원점, IMU 몸체 기울기, 쿠션/바닥 접촉을 외부 영상과 대조 |
| 오류·전압 저하·통신 누락이 동반됨 | 전원·배선·통신 문제부터 분리 |

이 보고서는 특정 조건에서의 **관측된 동작 능력**이다. 부하/전류 원시값을 정확한 Nm/A로 환산하지 않으며, 전압과 오차의 동시 변화만으로 원인을 단정하지 않는다. 관절 위치만으로 실제 접촉력을 측정했다고 하지 않는다.

## 시간 해상도와 다음 단계

일반 보행은 1축/20ms 순차 조회이므로 한 관절은 대략240ms마다 읽힌다. 샘플 사이 위치 차이로 구한 속도는 **구간 평균 속도**이며 최고 속도가 아니다. 전송·조회 시작/종료 시각은 통신의 시간 범위이며 서보 내부 ADC/엔코더 샘플 시각이 아니다.

분석기는 조밀한 명령 이력과 실측값을 비교해 지연 후보를 계산하지만, 부족한 시간 해상도·여러 가능한 지연·작은 입력·데이터 부족이면 `delay_estimate_ms=null`로 남긴다. `delay_candidate_ms`만 있는 값은 확정값이 아니다. 고정 오프셋, 탄성, 동역학이 시간 지연과 섞일 수 있다. 모터의 매개변수가 식별됐다고 선언하지 않는다.

**두 번째 시험 제안(아직 자동 구동 기능으로 구현하지 않음):** 첫 시험에서 문제 축을 좁힌 뒤 몸체와 나머지 다리를 고정한 벤치에서 해당 축을 좁은 범위로 양방향 구동하고, 단일 축 고속 조회 또는 외부 고속 영상/엔코더로 지연·가속·하중별 응답을 측정한다. 보행 중 다른11축 안전 감시를 빼고 한 축만 빨리 읽는 방식은 채택하지 않는다. 무부하와 알려진 하중을 구분해야 토크-속도 특성을 식별할 수 있다. 스윙/지지 데이터만으로 정확한 정격 토크를 역산하지 않는다.

## MuJoCo 반영 기준

현재 분석기는 물리 파라미터를 자동 변경하지 않는다. 반복 측정으로 신뢰 구간이 확보된 관절별 지연/속도/추종 특성만 별도의 실측 프로파일로 반영한다. 식별에 쓰지 않은 전진·좌우 턴 기록으로 예측 오차를 다시 검사한 뒤 적용한다. 고장이 없다는 결과나 보행 성공을 미리 만들어 넣지 않는다.

## 검증

- C 기록기: 준비 전 무기록, 기록 복사, 읽기 실패 보존, 용량 도달 시 덮어쓰기 방지, 재준비, 타이머 순환.
- Python: 알려진 합성 지연, 240ms 관측에서 확정 지연 억제, signed 목표와 단회전 피드백 경계, 누락/잘못된 시각 거부, 읽기 실패 제외, 분석 구간, 미측정 축을0으로 표시하지 않음, 오프라인 CLI, dump 타임아웃.
- 보행 루프의 기존 회귀를 함께 실행. V47 readback, Landing/Stand 전환 및 전진/좌/우 단기시험을 실시했다. 장기·다조건 검증 및 정밀응답 식별은 미실시.
- 합성 검증은 실제 모터 성능 결과가 아니다.

## 실기 검증 결과 (2026-09-12 추가)

V46의 한 번에 전체 덤프 방식에서 BLE 전송 누락과 타임아웃이 발견됐다. V47에서 최대12개씩 요청·검증하도록 수정했으며, 전진252/252개, 좌회전241/241개, 우회전241/241개의 명령/측정 기록을 끝까지 확인했다. 40개 호스트 검사가 통과했다.

[실측 및 MuJoCo 재생 비교 보고서](JOINT-CAPABILITY-VALIDATION-2026-09-12.md)를 참고한다. 실물의 실제 명령을 재생했으며, 모델의 질량·마찰·모터 파라미터를 이번 데이터에 맞춰 변경하지 않았다.
